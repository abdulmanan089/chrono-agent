Chrono Agent Audit Report

A hands-on test of the Chrono Agent MCP server on Windows 11. It covers the command gate, false positives on normal developer commands, snapshot and rollback recovery, and the tamper-evident audit chain. The first audit of release 0.4.1rc2 found six gaps. Release 0.5.0 fixes them. This page shows the 0.5.0 re-test first and keeps the original audit below as the record.

Verdict for 0.5.0
All six findings fixed and re-tested. Ready for a public developer release.

Re-running every probe of the original audit against 0.5.0 gave 30 passes out of 30. That includes the attack 0.4.1rc2 missed: deleting an audit record and recomputing every later hash is now detected. The unit suite and the red-team suite run clean on Windows. Chrono is still not a sandbox, and keys in the user's own home folder can be read by that same OS account. Before Chrono is sold as an enterprise security product, an independent human penetration test is still needed. No release can honestly be called "100% ready".

Limits that remain by design

  • Not a sandbox. An allowed program can do anything the OS account can. Variables and payloads decoded at run time, compiled programs and imported modules are not inspected.
  • Local trust boundary. Signing keys, witnesses and policy pins live in the user's Chrono home. The same OS account can read them. Use a vault key (CHRONO_AUDIT_KEY) and chrono audit --push to a store the agent cannot reach.
  • Coverage. Only paths through Chrono are enforced: MCP chrono_run, the guard hook and chrono run. An unguarded shell, an IDE plugin or a person at a terminal are outside.
  • Identity. Approvals and roles are named, not authenticated, and agent labels are not workload identities.
  • Rollback scope. Project files only, never registry, services, shadow copies, outside files or network effects.

Release readiness

Ready now (0.5.0)

  • Public open-source release as a developer tool, with SECURITY.md stating its limits
  • Use with Claude Code and other MCP clients on development machines
  • Demos of blocking, script inspection, savepoints, rollback and signed audit

Before an enterprise security launch

  • An independent human penetration test, including scanner-evasion testing
  • CI green on Linux and macOS (the workflow is included but has not run)
  • The guard tested inside live Claude Code sessions
  • Signing for the fleet gateway's own event chain

Original hardening assessment (0.4.1rc2)

High

H1 · Audit log is unsigned by default

Fixed in 0.5.0

Without CHRONO_AUDIT_KEY the chain used plain SHA-256, so test A4 could rebuild it after a deletion.

High

H2 · Enforcement covers only chrono_run

Fixed in 0.5.0

Nothing stopped an agent from running the same command through another shell tool.

Medium

H3 · Scanner reads command text, not behaviour

Fixed in 0.5.0

python app.py scored LOW whatever the script contained.

Medium

H4 · Rollback cannot undo system-level damage

Documented in 0.5.0

Savepoints cover tracked project files only. This is still true by design, and it is now stated in every run and rollback reply.

Low

H5 · A savepoint for every allowed command

Fixed in 0.5.0

Three read-only commands produced three savepoints.

Low

H6 · Registry rule blocks every reg add

Fixed in 0.5.0

Blocking every edit was safe, but it also stopped legitimate developer setup.

Scope and limits of this report

  • This is a scoped functional test run by an AI assistant. It is not a formal certification or a third-party security audit, and it should not be presented as one.
  • The same assistant that ran the 0.4.1rc2 audit also wrote the 0.5.0 fixes and ran the re-test, so the re-test is not independent.
  • Not tested: scanner evasion and obfuscation robustness, Linux and macOS, the guard inside a live Claude Code session, Postgres/MySQL rollback, and the git hook (git is not installed on this machine).
  • Catastrophic commands against the real system were scanned, not executed.
  • No software can honestly be certified "100% ready". The verdicts above describe readiness for specific uses.

Details in the release ZIP: docs/REMEDIATION.md maps each finding to code and tests; VERIFICATION.md and RED_TEAM_REPORT.md hold the Windows results; SECURITY.md states the threat model.
